# GoodThingz Page Layout

작성일: 2026-08-27

기준 문서:

- `docs/product/service-design.md`
- `docs/ui/design-system.md`
- `docs/seo/index-policy.md`

이 문서는 GoodThingz 첫 버전의 화면별 UX 설계다. 아직 코드를 작성하지 않고, 각 화면에서 사용자가 무엇을 하려는지, 어떤 정보를 먼저 봐야 하는지, 어떤 버튼이 필요한지를 정리한다.

## 1. 홈페이지

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | GoodThingz가 무엇을 해주는지 빠르게 이해하고, 반려동물 동반여행 검색을 바로 시작한다. |
| 가장 중요한 정보 | “반려동물과 갈 수 있는 곳을 조건까지 확인한다”는 서비스 가치, 무료 정책, 데이터 출처, 검색 시작 진입점 |
| 주요 버튼 | `반려동물 여행지 찾기`, `현재 위치로 찾기`, `데이터 출처 보기` |
| 정보 우선순위 | 1. 검색 시작 2. 서비스가 줄여주는 시간 3. 무료 정책 4. 데이터 출처와 기준 5. SEO용 소개 정보 |

홈페이지는 마케팅용 장식 페이지가 아니라 서비스 진입점이어야 한다. 첫 화면 안에서 사용자가 바로 `/pet-travel`로 이동하거나 현재 위치 검색을 시작할 수 있어야 한다. 단, 현재 위치 권한 요청은 홈 진입 즉시 띄우지 않고 사용자가 버튼을 눌렀을 때만 요청한다.

홈에는 결제 없음, 구독 없음, Paywall 없음을 짧게 표시하되 크게 과시하지 않는다. 서비스 신뢰를 위해 한국관광공사 반려동물 동반여행 공공데이터를 사용한다는 출처 링크와 데이터 기준일을 제공한다.

## 2. 핵심 서비스 페이지

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 현재 위치, 지역, 키워드 중 하나로 빠르게 후보 검색을 시작한다. |
| 가장 중요한 정보 | 검색 바, 지역 선택, 현재 위치 버튼, 주요 필터, 데이터 기준일 |
| 주요 버튼 | `검색`, `현재 위치 사용`, `지역 선택`, `필터 열기`, `초기화` |
| 정보 우선순위 | 1. 검색 입력 2. 검색 방식 선택 3. 기본 필터 4. 최근/추천 아님, 목적별 빠른 시작 5. 출처와 기준일 |

핵심 서비스 페이지 `/pet-travel`은 첫 버전의 중심 화면이다. 상단에는 “어디에서 찾을까요?”보다 구체적인 검색 행동을 배치한다. 예를 들어 지역 선택, 키워드 입력, 현재 위치 사용을 한 줄에서 선택할 수 있게 한다.

아직 사용자가 검색하지 않은 상태에서는 인기 순위나 추천 순위를 보여주지 않는다. API에 리뷰나 실제 만족도 데이터가 없기 때문이다. 대신 “현재 위치 주변”, “지역으로 찾기”, “숙소 주변 후보 확인”처럼 문제 해결형 시작점을 제공한다.

## 3. 검색/필터

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 후보를 너무 많이 보지 않고 자신의 상황에 맞는 범위로 줄인다. |
| 가장 중요한 정보 | 지역/위치/키워드, 장소 유형, 거리 반경, 정보 상태, 주차/전화/이미지 유무 |
| 주요 버튼 | `검색`, `현재 위치 사용`, `필터 적용`, `필터 초기화`, `확인 필요 포함` |
| 정보 우선순위 | 1. 검색 기준 2. 장소 유형 3. 거리 반경 4. 방문 판단 정보 5. 보조 조건 |

검색/필터는 기본값이 너무 복잡하면 안 된다. 첫 버전의 기본 필터는 장소 유형, 거리 반경, 전화번호 있음, 이미지 있음, 반려동물 조건 있음, 주차 정보 있음, 확인 필요 포함으로 제한한다. 사용자가 조건을 조정할 때마다 결과 수가 어떻게 바뀌는지 보여주면 불필요한 재검색을 줄일 수 있다.

필터 이름은 API field가 아니라 사용자 언어로 쓴다. `contentTypeId=39`가 아니라 `음식점`, `firstimage`가 아니라 `사진 있음`, `tel`이 아니라 `전화 확인 가능`이다. 빈 값은 제외 조건으로 단정하지 않고 “정보 없음” 상태로 남긴다.

## 4. 결과 목록

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 후보들을 빠르게 훑고, 갈 만한 곳을 상세 확인 또는 비교에 넣는다. |
| 가장 중요한 정보 | 장소명, 유형, 거리, 주소, 사진, 정보 상태, 반려동물 조건 요약 |
| 주요 버튼 | `상세 보기`, `비교 추가`, `전화`, `지도에서 보기`, `더 보기` |
| 정보 우선순위 | 1. 장소명과 유형 2. 거리와 주소 3. 정보 상태 4. 조건 요약 5. 다음 행동 |

결과 목록은 정보 밀도가 높아야 하지만 피곤하면 안 된다. 각 카드의 첫 줄에는 장소명과 유형, 둘째 줄에는 거리와 주소, 그 아래에는 조건 상태와 짧은 요약을 둔다. 정보가 모호하면 “확인 필요”를 숨기지 말고 카드에서 바로 보이게 한다.

정렬은 거리순, 최신 수정순, 이름순, 사진 있는 결과 우선을 제공한다. “추천순”은 API 근거가 부족하므로 첫 버전에서 사용하지 않는다. 페이지네이션은 `더 보기` 또는 페이지 이동으로 처리하되, 현재 `page`, `pageSize`, `totalCount`, `hasNextPage`를 기반으로 결과 규모를 알려준다.

## 5. 비교 화면

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 후보 2~3개 중 어디를 갈지 조건을 나란히 보고 결정한다. |
| 가장 중요한 정보 | 거리, 유형, 주소, 전화 가능 여부, 주차 정보, 운영 정보, 반려동물 조건, 확인 필요 상태 |
| 주요 버튼 | `후보 제거`, `상세 보기`, `전화`, `공유`, `검색으로 돌아가기` |
| 정보 우선순위 | 1. 결정 차이가 큰 항목 2. 반려동물 조건 3. 이동/위치 4. 운영/주차 5. 이미지와 출처 |

비교 화면은 모든 field를 표로 늘어놓는 화면이 아니다. 사용자가 실제로 선택을 바꾸게 만드는 항목을 먼저 보여준다. 예를 들어 “조건 명확함”, “전화 확인 권장”, “주차 정보 있음”, “거리”는 위쪽에 두고, 원문 설명과 이미지 상세는 아래로 내린다.

비교 대상은 첫 버전에서 2~3개가 적절하다. 모바일에서 4개 이상 비교는 읽기 어렵고, 데이터 호출도 늘어난다. 정보가 없는 항목은 빈칸이 아니라 `정보 없음`으로 표시하고, 조건이 모호한 항목은 `확인 필요`로 표시한다.

## 6. 상세 페이지

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 이 장소에 실제로 갈지, 전화 확인이 필요한지, 준비물이 필요한지 판단한다. |
| 가장 중요한 정보 | 반려동물 조건 요약, 전화번호, 주소, 운영/주차 정보, 정보 부족 경고, 원문 근거 |
| 주요 버튼 | `전화`, `지도에서 보기`, `비교 추가`, `공유`, `검색 결과로 돌아가기` |
| 정보 우선순위 | 1. 방문 판단 요약 2. 전화/지도 행동 3. 반려동물 조건 4. 운영/주차 5. 이미지 6. 원문/출처 |

상세 페이지는 장소 홍보 페이지가 아니라 방문 판단 페이지다. 상단에는 장소명과 유형, 주소, 핵심 상태를 두고, 바로 아래에 “방문 전 확인할 것”을 보여준다. 전화번호가 있으면 전화 버튼을 눈에 잘 보이게 배치하고, 전화번호가 없으면 대체 행동으로 홈페이지 또는 원문 확인을 제공한다.

반려동물 조건은 `동반 가능 동물`, `필요 준비물`, `주의사항`, `관련 시설`, `구매·대여 가능 품목`처럼 의미 단위로 정리한다. 단, 대형견 가능 여부처럼 원문이 명확하지 않은 정보는 가능하다고 단정하지 않는다. 원문 근거와 출처, 데이터 기준일은 상세 하단에서 확인할 수 있어야 한다.

## 7. Empty State

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 결과가 없을 때 막히지 않고 다음 검색 행동을 선택한다. |
| 가장 중요한 정보 | 결과가 없는 이유, 바꿔볼 수 있는 조건, 데이터 한계 |
| 주요 버튼 | `반경 넓히기`, `필터 줄이기`, `지역 다시 선택`, `확인 필요 포함`, `처음으로` |
| 정보 우선순위 | 1. 상태 설명 2. 즉시 가능한 해결 버튼 3. 데이터 한계 4. 출처 |

Empty State는 “검색 결과 없음” 한 줄로 끝내면 안 된다. 사용자가 시간을 줄이기 위해 온 서비스이므로 바로 다음 행동을 제공해야 한다. 예를 들어 위치 기반 검색에서 결과가 없으면 반경을 넓히고, 필터가 많으면 필터를 줄이고, 조건이 너무 엄격하면 확인 필요 후보를 포함하도록 제안한다.

API가 정상적으로 빈 결과를 준 경우와 입력이 너무 제한적인 경우를 구분한다. 빈 결과는 오류가 아니므로 빨간색 경고를 쓰지 않는다.

## 8. Error State

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 무엇이 잘못됐는지 이해하고 다시 시도하거나 다른 검색으로 전환한다. |
| 가장 중요한 정보 | 사용자 입력 오류인지, API 오류인지, 네트워크 오류인지, 다시 시도 가능 여부 |
| 주요 버튼 | `다시 시도`, `검색 조건 수정`, `처음으로`, `문제 보고` |
| 정보 우선순위 | 1. 쉬운 오류 설명 2. 복구 행동 3. 오류 기준 4. 기술 상세는 숨김 |

Error State는 사용자를 탓하지 않아야 한다. 입력 오류는 “page는 1 이상이어야 합니다”처럼 구체적으로 보여주고, API 오류는 “공공데이터를 잠시 불러오지 못했습니다”처럼 이해 가능한 말로 보여준다. Secret 이름, API Key, 원본 요청 URL, 원본 오류 전문은 UI에 노출하지 않는다.

timeout은 “응답이 오래 걸려 중단했습니다”로 안내하고 다시 시도 버튼을 제공한다. 반복 오류가 있으면 지역 검색이나 키워드 검색처럼 다른 진입점으로 돌아갈 수 있어야 한다.

## 9. Loading State

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 지금 무엇을 기다리는지 이해하고 화면이 멈춘 것이 아니라고 느낀다. |
| 가장 중요한 정보 | 데이터 확인 중인 범위, 검색 조건 요약, 취소 또는 재시도 가능성 |
| 주요 버튼 | 첫 버전에서는 별도 버튼 없음, 긴 로딩에는 `다시 시도` 또는 `검색 수정` 제공 |
| 정보 우선순위 | 1. 로딩 메시지 2. skeleton 목록 3. 지도 placeholder 4. 기준 조건 |

검색 로딩은 전체 화면을 비워두지 않는다. 검색 바와 필터 요약은 그대로 두고, 결과 영역에 skeleton card를 표시한다. 지도 영역은 회색 placeholder나 이전 지도 상태를 유지한다.

상세 정보 로딩은 전체 페이지 로딩보다 부분 로딩이 좋다. 장소 기본 정보가 이미 있으면 먼저 보여주고, 반려동물 조건과 운영 정보는 “상세 조건 확인 중” 상태로 나중에 채운다.

## 10. 모바일 화면

| 항목 | 설계 |
| --- | --- |
| 사용자의 목적 | 이동 중에도 한 손으로 검색하고, 가까운 후보를 빠르게 고른다. |
| 가장 중요한 정보 | 검색 조건 요약, 결과 카드, 거리, 상태 배지, 전화 버튼 |
| 주요 버튼 | `현재 위치`, `필터`, `목록`, `지도`, `상세`, `전화`, `비교` |
| 정보 우선순위 | 1. 현재 검색 기준 2. 가까운 후보 3. 정보 상태 4. 전화/상세 행동 5. 지도 전환 |

모바일 기본 화면은 목록 우선이다. 지도는 탭으로 전환하거나 하단에서 끌어올리는 방식으로 제공한다. 필터는 바텀시트로 열고, 적용 버튼과 초기화 버튼을 하단에 고정한다.

결과 카드의 높이는 과도하게 커지지 않아야 한다. 장소명, 유형, 거리, 주소, 상태 배지, 전화/상세 버튼만 먼저 보이고, 긴 반려동물 조건은 1~2줄 요약 후 상세에서 확인하게 한다. 비교는 하단 고정 tray로 제공하되, 화면을 가리지 않도록 접힌 상태를 기본으로 한다.

## 11. 화면 간 흐름

```text
홈
  -> 핵심 서비스 페이지
    -> 검색/필터
      -> 결과 목록
        -> 상세 페이지
        -> 비교 화면
        -> Empty State
        -> Error State
```

사용자는 언제든 검색 조건으로 돌아갈 수 있어야 한다. 상세나 비교 화면에서 뒤로 가면 이전 검색 조건과 스크롤 위치가 유지되어야 한다. 모바일에서는 이 흐름이 끊기면 사용자가 다시 검색해야 하므로, 검색 상태 유지가 매우 중요하다.

첫 버전에서는 화면을 SEO 페이지로 늘리지 않는다. 검색 결과, 상세, 비교는 사용성에는 중요하지만 sitemap에 넣지 않고 `noindex,follow`를 기본으로 한다.
