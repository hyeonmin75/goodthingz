# GoodThingz UI Design System

작성일: 2026-08-27

기준 문서:

- `docs/product/service-design.md`
- `docs/value/value-map.md`
- `docs/seo/index-policy.md`

이 문서는 GoodThingz의 첫 UI를 무료지만 전문 상용 데이터 서비스처럼 느껴지게 만들기 위한 공통 디자인 기준이다. 목표는 화려한 장식이 아니라 문제 해결 속도, 정보 이해 속도, 비교 용이성, 모바일 편의성이다.

## 1. 디자인 원칙

GoodThingz는 “반려동물 동반 가능 장소 목록”을 보여주는 앱이 아니라 “지금 갈 수 있는 후보를 빠르게 판단하게 하는 데이터 서비스”다. 따라서 첫 화면부터 검색 행동을 막는 긴 홍보 영역을 두지 않고, 사용자가 지역, 위치, 키워드 중 하나로 바로 시작할 수 있어야 한다.

UI는 차분하고 실무적인 데이터 서비스처럼 보여야 한다. 정보가 많은 화면에서도 시선이 흔들리지 않도록 색은 상태와 행동을 구분하는 데 사용하고, 장식용 그라데이션이나 큰 시각 효과는 피한다. 사용자는 “예쁘다”보다 “빨리 찾았다”, “조건을 바로 이해했다”, “전화해야 할 곳을 알았다”고 느껴야 한다.

## 2. 정보 표현 원칙

| 원칙 | 적용 방식 |
| --- | --- |
| 원본 field 노출 금지 | `contenttypeid`, `acmpyNeedMtr` 같은 API field 이름은 UI에 직접 보이지 않는다. |
| 판단 언어 사용 | “쇼핑”, “주차 정보 있음”, “반려동물 조건 확인 필요”처럼 사용자가 행동으로 옮길 수 있는 말로 바꾼다. |
| 모르는 것은 모른다고 표시 | 빈 값은 “불가”가 아니라 “정보 없음”으로 표시한다. |
| 확인 필요 분리 | “정보 없음”, “조건 모호”, “전화 확인 권장”을 같은 의미로 섞지 않는다. |
| 과장 금지 | 실시간 영업, 예약 가능 여부, 가격, 리뷰, 만족도는 API에 없으므로 있는 것처럼 표현하지 않는다. |
| 출처 표시 | 데이터 기준일, 제공기관, 갱신 기준을 핵심 화면에서 확인할 수 있게 한다. |

## 3. 레이아웃 시스템

기본 레이아웃은 데스크톱에서 넓은 화면을 잘 쓰는 2단 구조를 우선한다. 검색과 필터는 왼쪽 또는 상단에 고정하고, 결과 목록과 지도는 함께 보이게 한다. 모바일에서는 한 화면에 모든 것을 밀어 넣지 않고, 검색, 필터, 목록, 지도를 탭이나 바텀시트로 전환한다.

| 화면 크기 | 기본 구조 | 목적 |
| --- | --- | --- |
| 데스크톱 1200px 이상 | 상단 검색 바 + 좌측 결과 목록 + 우측 지도/상세 보조 패널 | 비교와 위치 파악을 동시에 처리 |
| 태블릿 768px 이상 | 상단 검색 바 + 목록 중심 + 지도 접기/펼치기 | 공간을 아끼면서 필터 유지 |
| 모바일 360px 이상 | 상단 검색 요약 + 필터 바텀시트 + 목록 우선 + 지도 탭 | 이동 중 한 손 조작과 빠른 스캔 |

카드는 반복 항목인 장소 결과, 비교 후보, 상태 안내에만 사용한다. 페이지 섹션 전체를 큰 카드로 감싸지 않는다. 카드 반경은 8px 이하로 유지하고, 정보 밀도를 지나치게 낮추지 않는다.

## 4. 색상 체계

색상은 반려동물 서비스처럼 따뜻하되, 데이터 서비스답게 안정적이어야 한다. 한 가지 색 계열만 화면을 지배하지 않게 하고, 상태 색상은 의미가 분명해야 한다.

| 역할 | 제안 색상 | 사용처 |
| --- | --- | --- |
| Primary | 짙은 청록 `#0F766E` | 주요 검색 버튼, 선택된 필터, 현재 위치 버튼 |
| Primary Soft | 옅은 청록 `#E6F4F1` | 선택 상태 배경, 정보 태그 |
| Text Strong | 거의 검정 `#111827` | 제목, 장소명, 핵심 수치 |
| Text Default | 회색 `#374151` | 본문, 주소, 설명 |
| Text Muted | 회색 `#6B7280` | 보조 정보, 출처, 기준일 |
| Border | 연한 회색 `#D1D5DB` | 입력, 카드, 구분선 |
| Surface | 흰색 `#FFFFFF` | 기본 배경 위 콘텐츠 |
| Page | 아주 옅은 회색 `#F8FAFC` | 페이지 배경 |
| Success | 녹색 `#15803D` | 정보 확인됨, 조건 있음 |
| Warning | 호박색 `#B45309` | 전화 확인 권장, 조건 모호 |
| Danger | 빨강 `#B91C1C` | API 오류, 잘못된 입력 |

색만으로 상태를 전달하지 않는다. 예를 들어 경고는 색상과 함께 “전화 확인 권장” 텍스트를 반드시 표시한다.

## 5. Typography

기본 글꼴은 시스템 UI 또는 한국어 가독성이 좋은 sans-serif 계열을 사용한다. 현재 프로젝트가 Inter를 쓰고 있지만 한국어 본문에는 시스템 폰트 fallback이 중요하다.

| 역할 | 크기 | 굵기 | 용도 |
| --- | --- | --- | --- |
| Page title | 28~32px | 700 | 홈, 핵심 서비스 페이지의 핵심 제목 |
| Section title | 20~24px | 700 | 결과 그룹, 상세 섹션 |
| Card title | 17~19px | 700 | 장소명, 비교 후보명 |
| Body | 15~16px | 400~500 | 주소, 설명, 요약 |
| Meta | 13~14px | 400 | 기준일, 거리, 출처 |
| Control | 14~16px | 600 | 버튼, 필터, 탭 |

버튼과 태그 안의 텍스트는 줄바꿈이 생겨도 깨지지 않게 최소 너비와 줄 높이를 잡는다. 글자 크기를 viewport 너비에 비례해 무리하게 키우지 않는다.

## 6. 컴포넌트 기준

### 6.1 Search Bar

검색 바는 GoodThingz의 가장 중요한 컴포넌트다. 사용자는 “현재 위치”, “지역 선택”, “키워드” 중 하나로 바로 시작할 수 있어야 한다. 기본 상태에서는 입력창, 지역 선택 버튼, 현재 위치 버튼, 검색 버튼을 제공한다.

| 요소 | 역할 | 우선순위 |
| --- | --- | --- |
| 키워드 입력 | 장소명이나 목적 검색 | P0 |
| 지역 선택 | 시도·시군구 기반 검색 | P0 |
| 현재 위치 | 주변 반경 검색 | P0 |
| 검색 버튼 | 조건 실행 | P0 |
| 최근 검색 | 반복 사용 보조 | P1 |

현재 위치는 사용자의 브라우저 권한이 필요하므로 “현재 위치 사용” 버튼을 누른 뒤 권한을 요청한다. 권한 거부 시 지역 검색으로 자연스럽게 돌아갈 수 있어야 한다.

### 6.2 Filter Controls

필터는 사용자를 압박하지 않게 기본 필터와 상세 필터를 나눈다. 첫 화면에는 장소 유형, 반경, 정보 상태 정도만 보이고, 상세 필터는 펼쳐서 보게 한다.

| 필터 | 표현 방식 | 이유 |
| --- | --- | --- |
| 장소 유형 | segmented control 또는 checkbox group | 관광지, 숙박, 음식점처럼 복수 선택이 자연스럽다. |
| 거리 반경 | slider 또는 segmented control | 1km, 3km, 5km, 10km처럼 빠른 선택이 필요하다. |
| 이미지 있음 | toggle | 분위기 판단이 필요한 사용자에게 유용하다. |
| 전화번호 있음 | toggle | 전화 확인이 필요한 사용자에게 유용하다. |
| 반려동물 조건 있음 | toggle | 조건 해석 시간을 줄인다. |
| 주차 정보 있음 | toggle | 이동 사용자의 실패 비용을 줄인다. |
| 확인 필요 포함 | toggle | 모호한 후보를 볼지 숨길지 선택한다. |

필터 결과 수는 즉시 보여준다. 예를 들어 “조건에 맞는 후보 18곳”처럼 결과 규모를 알려주면 사용자가 필터를 더 줄일지 판단하기 쉽다.

### 6.3 Place Result Card

결과 카드는 빠른 스캔을 위해 장소명, 유형, 거리, 주소, 핵심 상태를 위에서부터 보여준다. 이미지가 있으면 왼쪽 또는 상단에 작게 배치하되, 이미지가 없는 장소도 정보가 무너지지 않아야 한다.

| 정보 | 표시 방식 | 이유 |
| --- | --- | --- |
| 장소명 | 카드 제목 | 후보 식별 |
| 장소 유형 | 작은 태그 | 관광지, 숙박, 음식점 빠른 구분 |
| 거리 | 강한 보조 정보 | 이동 부담 판단 |
| 주소 | 한두 줄 | 지역 확인 |
| 정보 상태 | 상태 배지 | 확인됨, 일부 부족, 전화 확인 권장 |
| 반려동물 조건 요약 | 1~2줄 | 상세 진입 전 판단 |
| 주요 버튼 | 상세, 비교 추가, 전화 | 다음 행동 |

카드에는 “추천” 같은 품질 판단 단어를 쓰지 않는다. API가 말할 수 있는 것은 후보의 위치, 유형, 조건, 정보 상태이지 실제 만족도가 아니다.

### 6.4 Status Badge

상태 배지는 GoodThingz의 신뢰를 만드는 핵심 요소다.

| 상태 | 문구 | 의미 |
| --- | --- | --- |
| 확인됨 | 조건 정보 있음 | API에 판단 가능한 반려동물 조건 정보가 있다. |
| 일부 부족 | 일부 정보 없음 | 전화, 운영, 주차, 이미지 중 일부가 없다. |
| 확인 필요 | 전화 확인 권장 | 조건이 모호하거나 핵심 정보가 부족하다. |
| 정보 없음 | 공식 정보 없음 | 해당 field가 비어 있다. |
| API 오류 | 데이터를 불러오지 못함 | 외부 API 또는 내부 처리 오류다. |

상태 문구는 부정확한 확신보다 정직한 안내를 우선한다. “가능”보다 “조건 정보 있음”이 더 안전하다.

### 6.5 Comparison Tray

비교 후보는 화면 하단 또는 우측에 작게 고정한다. 사용자가 2개 이상 선택하면 비교 버튼이 활성화된다. 최대 3개를 기본으로 하여 모바일에서도 부담 없이 비교하게 한다.

비교 후보에는 장소명, 유형, 거리, 제거 버튼만 둔다. 너무 많은 정보를 tray에 넣으면 결과 목록을 가린다.

### 6.6 Detail Decision Panel

상세 화면은 소개 글보다 방문 판단을 먼저 보여준다. 상단에는 장소명, 유형, 주소, 전화 버튼, 지도 보기, 비교 추가를 배치한다. 그 아래에는 반려동물 조건 요약, 운영·주차 정보, 정보 부족 경고, 원문 근거, 이미지, 출처 순서로 배치한다.

원문 근거는 접을 수 있게 하되 숨겨서는 안 된다. 조건이 까다로운 사용자는 원문을 확인해야 안전하게 판단할 수 있다.

### 6.7 Buttons

버튼은 명령이 분명해야 한다.

| 버튼 | 우선순위 | 표현 |
| --- | --- | --- |
| 검색 | Primary | 검색 실행 |
| 현재 위치 사용 | Secondary | 위치 권한 요청 |
| 상세 보기 | Secondary | 방문 판단 카드 열기 |
| 비교 추가 | Icon + text | 후보 비교에 추가 |
| 전화 | Icon + text | `tel:` 연결 가능할 때 |
| 공유 | Icon | P1 기능, 개인정보 주의 |
| 다시 시도 | Primary | 오류 복구 |
| 필터 초기화 | Tertiary | 조건 리셋 |

아이콘은 구현 단계에서 lucide-react 같은 기존 아이콘 라이브러리를 사용할 수 있다. 아이콘만 있는 버튼에는 tooltip과 접근 가능한 label을 제공한다.

## 7. 상태 화면 기준

### Loading

로딩은 사용자가 기다리는 이유를 알 수 있어야 한다. “불러오는 중”만 보여주지 말고 “반려동물 동반여행 데이터를 확인하는 중”처럼 현재 작업을 알려준다. 결과 목록은 skeleton card를 사용하고, 지도는 흐릿한 placeholder로 유지한다.

### Empty

empty는 실패가 아니라 다음 행동을 제안하는 상태다. “조건에 맞는 결과가 없습니다” 다음에 반경 넓히기, 필터 줄이기, 지역 바꾸기, 확인 필요 포함하기 같은 버튼을 제공한다.

### Error

error는 사용자 잘못과 서비스/API 문제를 분리한다. 잘못된 입력은 입력 위치 근처에 보여주고, 공공데이터 API 오류는 전체 안내로 보여준다. API Key, 내부 endpoint, 원본 응답 body처럼 민감하거나 복잡한 정보는 사용자 화면에 노출하지 않는다.

## 8. 접근성 기준

모든 주요 기능은 키보드로 접근 가능해야 한다. 검색 입력, 필터, 결과 카드, 비교 추가, 상세 닫기, 전화 버튼은 tab 순서가 자연스러워야 한다. 지도만으로 정보를 전달하지 않고, 같은 후보가 목록에도 표시되어야 한다.

색 대비는 본문과 버튼에서 충분히 확보한다. 상태는 색만으로 전달하지 않고 텍스트를 함께 제공한다. 모바일 터치 영역은 최소 44px 이상을 목표로 한다.

## 9. 모바일 기준

모바일은 이동 중 사용자가 많으므로 목록 스캔과 한 손 조작을 우선한다. 지도는 전체 화면 전환 또는 하단 탭으로 제공하고, 기본은 목록이다. 필터는 바텀시트로 열며, 적용 버튼과 초기화 버튼은 하단에 고정한다.

모바일 결과 카드는 한 화면에 2~3개가 보일 정도의 정보 밀도를 유지한다. 긴 설명은 상세 화면으로 보내고, 목록에는 거리, 유형, 주소, 조건 상태, 전화 확인 여부만 남긴다.

## 10. 품질 기준

GoodThingz의 UI 품질은 “기능이 많음”이 아니라 “판단이 빠름”으로 평가한다. 첫 버전 QA에서는 다음을 확인한다.

- 검색 시작까지 한 화면 안에서 가능하다.
- 결과 카드에서 장소 유형, 거리, 주소, 정보 상태가 즉시 보인다.
- 정보 없음과 확인 필요가 구분된다.
- 비교 후보를 추가하고 제거하기 쉽다.
- 모바일에서 필터가 화면을 과도하게 가리지 않는다.
- API 오류가 사용자가 이해할 수 있는 말로 표시된다.
- 출처와 기준일을 찾을 수 있다.
