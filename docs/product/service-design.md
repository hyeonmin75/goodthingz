# GoodThingz 제품 기능 설계

작성일: 2026-08-27

기준 문서:

- `docs/api/api-spec.md`
- `docs/value/user-problems.md`
- `docs/value/value-map.md`

이 문서는 한국관광공사 반려동물 동반여행 공공데이터를 단순히 많이 보여주는 것이 아니라, 사용자가 실제로 “갈 수 있는지” 판단하는 시간을 줄이기 위한 제품 기능 설계다. 모든 핵심 기능은 무료로 제공하며, 결제, 구독, Paywall, Premium 잠금 기능은 만들지 않는다.

## 1. 제품 방향

GoodThingz의 첫 제품 가치는 “반려동물 동반 가능 장소 목록”이 아니라 “반려동물과 실제로 방문할 후보를 빠르게 좁히고, 조건을 이해하고, 헛걸음 위험을 줄이는 것”이다. 사용자는 API 원본 field를 보고 싶은 것이 아니라, 가까운지, 조건이 맞는지, 준비물이 필요한지, 전화 확인이 필요한지, 여러 후보 중 어디가 나은지를 알고 싶다.

첫 버전은 P0 기능 중심으로 만든다. P0는 사용자가 지금 장소를 찾고 판단하는 데 반드시 필요한 기능이고, P1은 사용 시간을 더 줄이는 고가치 확장, P2는 나중에 데이터 검증과 사용 패턴이 쌓인 뒤 검토할 기능이다.

## 2. 우선순위 기준

| 우선순위 | 의미 | 첫 버전 포함 여부 |
| --- | --- | --- |
| P0 | 검색 시간, 비교 시간, 판단 시간을 직접 줄이는 필수 기능 | 포함 |
| P1 | 있으면 사용자 가치가 크지만 첫 버전 없이도 핵심 흐름이 성립하는 기능 | 선택적 포함 또는 다음 버전 |
| P2 | 데이터 근거가 약하거나, 특정 사용자에게만 가치가 있거나, 운영 데이터가 더 필요함 | 첫 버전 제외 |

## 3. 첫 버전 P0 범위

첫 버전은 현위치 또는 지역 기반 검색, 조건을 줄이는 스마트 필터, 지도와 목록을 함께 보는 결과 화면, 반려동물 동반 조건 요약, 후보 2~3개 비교, 정보 부족 경고를 중심으로 설계한다. 이 조합은 주말 당일 외출 보호자, 이동 중 여행자, 조건이 까다로운 보호자의 핵심 문제를 가장 빠르게 해결한다.

상세 API는 모든 목록 항목에 한 번에 호출하지 않는다. `locationBasedList2`, `areaBasedList2`, `searchKeyword2`로 후보를 먼저 좁히고, 사용자가 관심을 보인 상위 후보, 비교에 담은 후보, 상세 화면에 들어간 후보에 대해서만 `detailCommon2`, `detailIntro2`, `detailPetTour2`, `detailImage2`를 호출한다. 이렇게 해야 개발계정의 일일 트래픽 제한을 아끼면서도 실제 판단에 필요한 정보를 제공할 수 있다.

## 5. P0 기능 상세 설계

### 5.1 검색

검색은 현위치 기반, 지역 기반, 키워드 기반 세 가지 입구를 제공한다. 현위치 기반은 `locationBasedList2`를 사용해 반경 안의 장소를 찾고, 지역 기반은 `areaBasedList2`와 법정동 코드를 사용하며, 키워드 기반은 `searchKeyword2`를 사용한다. 첫 버전의 검색 목적은 결과를 많이 보여주는 것이 아니라, 사용자가 판단할 수 있는 후보를 빠르게 만드는 것이다.

검색 결과 카드에는 장소명, 장소 유형, 주소, 거리, 대표 이미지, 전화번호 유무, 정보 부족 상태를 표시한다. 반려동물 상세 조건은 목록 전체에 무조건 붙이지 않고, 상위 후보, 비교 후보, 상세 화면에서 단계적으로 불러온다.

### 5.2 스마트 필터

스마트 필터는 사용자가 “내 상황에 안 맞는 후보”를 빠르게 제거하도록 돕는다. 첫 버전 필터는 장소 유형, 거리 반경, 이미지 있음, 전화번호 있음, 반려동물 조건 있음, 주차 정보 있음, 전화 확인 필요를 중심으로 잡는다.

필터는 원본 field를 그대로 노출하지 않는다. 예를 들어 `contenttypeid`는 `관광지`, `숙박`, `음식점` 같은 사용자 언어로 바꾸고, `acmpyNeedMtr`는 `준비물 정보`, `etcAcmpyInfo`는 `동반 안내`, `relaAcdntRiskMtr`는 `주의사항`처럼 정규화한다. 원본값이 비어 있으면 “불가”가 아니라 “정보 없음”으로 처리한다.

### 5.3 지도와 목록

지도는 단독 기능이 아니라 목록 판단을 돕는 보조 화면이다. 지도에는 위치 관계와 반경을 보여주고, 목록에는 조건 요약과 정보 상태를 보여준다. 사용자는 지도를 통해 가까운 후보를 이해하고, 목록을 통해 갈지 말지 판단한다.

지도에서 표시하는 거리는 API의 `dist` 또는 좌표 기반 거리다. 실제 차량 이동시간, 경로, 도로 상황은 API에 없으므로 표현하지 않는다. 이 제한을 명확히 해야 사용자가 지도를 내비게이션이나 실시간 영업 정보처럼 오해하지 않는다.

### 5.4 반려동물 조건 요약

반려동물 조건 요약은 GoodThingz의 가장 중요한 차별 기능이다. `detailPetTour2`의 원문 정보를 `동반 가능 동물`, `동반 가능 규모`, `준비물`, `주의사항`, `관련 시설`, `구매·대여 가능 품목`으로 나누어 보여준다.

요약은 원문을 벗어나 판단하지 않는다. 대형견 가능 여부가 원문에 명확하지 않으면 “대형견 가능”으로 바꾸지 않고, “대형견 여부 확인 필요”로 표시한다. 요약 옆에는 원문 근거를 볼 수 있는 영역을 둬서 사용자가 중요한 결정을 할 때 직접 확인할 수 있게 한다.

### 5.5 관련정보와 방문 판단 카드

상세 화면은 장소 소개 페이지가 아니라 방문 판단 카드로 설계한다. 카드의 핵심은 “지금 이 장소를 방문해도 되는가”를 판단하게 하는 정보다. 주소, 전화번호, 홈페이지, 운영시간, 휴무일, 주차, 대표 이미지, 반려동물 동반 조건, 정보 부족 경고를 한 화면에서 정리한다.

API에 없는 예약 가능 여부, 가격, 실시간 영업 여부, 실제 입장 가능 여부는 표시하지 않는다. 필요한 경우 “공식 API에서 확인되지 않음” 또는 “전화 확인 권장”으로 표시한다.

### 5.6 비교

비교는 첫 버전에서 최대 2~3개 후보를 대상으로 제공한다. 비교 항목은 거리, 장소 유형, 주소, 전화번호, 주차 정보, 운영정보, 반려동물 조건, 준비물, 주의사항, 정보 부족 상태를 중심으로 한다.

비교 기능은 사용자가 여러 탭을 열고 문장을 직접 읽는 시간을 줄이는 것이 목적이다. 다만 정보가 없는 후보를 나쁜 후보로 단정하지 않고, `정보 없음`, `확인 필요`, `확인됨` 상태를 분리한다.

### 5.7 정보 부족 경고

정보 부족 경고는 사용자의 실패 비용을 줄이는 기능이다. 전화번호 없음, 반려동물 조건 없음, 운영정보 없음, 주차정보 없음, 이미지 없음 같은 상태를 모아 “방문 전 확인 필요”로 보여준다.

이 기능은 장소 품질 점수가 아니다. 정보가 부족하다는 것은 API 원본에서 판단 근거가 부족하다는 뜻이다. 따라서 UI 문구도 “나쁨”이 아니라 “확인 필요” 중심으로 설계한다.

## 6. P1 기능 상세 설계

P1 기능은 첫 버전 이후 사용자의 반복 사용과 여행 계획 시간을 더 줄이기 위해 추가한다. P1의 핵심은 여행 계획자와 가족 단위 사용자가 후보를 저장하고, 공유하고, 숙소 주변 일정이 성립하는지 확인하게 하는 것이다.

계산기는 “예상 만족도”가 아니라 “반경 내 후보 수”와 “타입 다양성”을 계산한다. 예를 들어 숙소 후보 주변 5km 안에 음식점, 관광지, 산책 가능한 장소가 몇 개 있는지 보여주면 여행 계획 시간이 줄어든다. 이 값은 API 근거가 분명하므로 사용자에게 설명하기 쉽고, 추측 위험도 낮다.

즐겨찾기는 로그인 없이 브라우저 로컬 저장을 기본으로 한다. GoodThingz 정책상 핵심 기능 이용을 위해 로그인을 강요하지 않는다. 공유는 검색 조건 또는 장소 후보를 URL로 전달하되, 현재 위치 좌표 같은 민감한 정보는 사용자가 명시적으로 선택한 경우에만 포함한다.

## 7. P2 기능 상세 설계

차트는 지역별 장소 수, 타입별 분포, 최근 수정 콘텐츠 같은 운영자용 가치가 있다. 하지만 첫 버전 일반 사용자에게는 검색, 조건 요약, 지도, 비교보다 우선순위가 낮다. 또한 전체 통계를 만들려면 pagination과 일일 호출 제한을 고려해야 하므로, 통계가 완전한지 검증한 뒤 추가해야 한다.

예상값 계산은 첫 버전에서 만들지 않는다. 현재 API에는 리뷰, 가격, 예약 가능 여부, 혼잡도, 실시간 영업, 실제 입장 성공 여부가 없으므로 “만족도 예상”, “방문 성공 확률”, “추천 점수”를 만들면 추측이 된다. 나중에 자체 데이터나 검증 가능한 추가 데이터가 생기더라도 계산식과 근거를 사용자에게 투명하게 보여줄 수 있을 때만 검토한다.

## 8. 정규화 데이터 모델 방향

UI는 API 원본 field를 직접 사용하지 않는다. Worker 또는 서버 레이어에서 원본을 정규화한 뒤 UI에 전달한다. 첫 버전에서 필요한 정규화 개념은 다음과 같다.

| 정규화 개념 | 원본 데이터 예시 | UI 의미 |
| --- | --- | --- |
| `PlaceSummary` | `contentid`, `title`, `contenttypeid`, `addr1`, `addr2`, `mapx`, `mapy`, `dist`, `firstimage`, `tel` | 검색 결과와 지도 카드에 필요한 최소 장소 정보 |
| `PlaceType` | `contenttypeid`, `lclsSystm1~3` | 관광지, 숙박, 음식점 등 사용자 언어의 장소 유형 |
| `VisitInfo` | `restdate`, `usetime`, `parking`, 타입별 소개정보 | 방문 전 확인해야 하는 운영·주차 정보 |
| `PetPolicy` | `acmpyTypeCd`, `acmpyPsblCpam`, `acmpyNeedMtr`, `etcAcmpyInfo`, `relaAcdntRiskMtr` | 반려동물 동반 조건, 준비물, 주의사항 |
| `MediaInfo` | `firstimage`, `firstimage2`, `originimgurl`, `smallimageurl`, `cpyrhtDivCd` | 대표 이미지와 상세 이미지 |
| `InfoStatus` | field 존재 여부와 모호성 | 정보 충분, 일부 부족, 전화 확인 권장 |

`InfoStatus`는 품질 점수가 아니라 판단 근거 상태다. 사용자가 장소를 신뢰할 수 있는지보다, 방문 전 무엇을 더 확인해야 하는지를 알려주는 데 목적이 있다.

## 9. API 호출 전략

첫 검색은 목록 API를 사용한다. 현위치 검색은 `locationBasedList2`, 지역 검색은 `areaBasedList2`, 키워드 검색은 `searchKeyword2`를 호출한다. 응답은 `_type=json`을 기본으로 요청하되, 오류 응답은 XML일 수 있으므로 Adapter에서 함께 처리한다.

상세 정보는 사용자의 관심도가 생긴 뒤 호출한다. 사용자가 장소 카드를 열거나 비교에 추가하면 `detailCommon2`, `detailIntro2`, `detailPetTour2`, 필요한 경우 `detailImage2`를 호출한다. 상위 몇 개 후보에 대해 미리 상세를 붙이는 기능은 가능하지만, 일일 트래픽 제한을 고려해 개수와 조건을 보수적으로 잡는다.

`/areaCode2`, `/categoryCode2`는 공식 자료 간 불일치가 있으므로 첫 버전 구현 기준에서 제외한다. 지역과 분류 코드는 매뉴얼 v4.1에 있는 `ldongCode2`, `lclsSystmCode2`를 기준으로 검토한다.

## 10. SEO URL 정책

SEO는 페이지 수를 늘리는 것이 목표가 아니다. 사용자가 독립적으로 방문해도 충분한 가치가 있는 URL만 검색 index 후보가 될 수 있다.

| URL 유형 | 판정 | 이유 |
| --- | --- | --- |
| 서비스 홈 또는 반려동물 여행 검색 시작 페이지 | INDEX | 사용자가 독립적으로 방문해도 검색, 지역 선택, 서비스 가치가 있다. |
| 검색 결과 URL | NOINDEX | query, 위치, 필터 조합에 따라 대량 생성될 수 있고 독립 가치가 약하다. |
| 필터 조합 URL | DO NOT CREATE | 필터 조합별 대량 페이지 생성은 SEO 정책에 맞지 않는다. |
| 키워드만 바꾼 SEO 페이지 | DO NOT CREATE | 키워드 치환 페이지는 추가 가치가 없다. |
| 장소 상세 URL | NOINDEX | 앱 사용과 공유를 위해 상세 화면은 필요할 수 있지만, API 레코드 수만큼 자동 색인 페이지를 만들지 않는다. |
| 지역별 편집형 가이드 페이지 | P2에서 별도 검토 | 원본 데이터 이상의 분석, 지도, 비교, 요약이 충분할 때만 INDEX 후보가 될 수 있다. |

## 11. 첫 버전에서 만들지 않는 것

첫 버전에서는 결제, 구독, Paywall, Premium 잠금, 핵심 기능 이용을 위한 로그인 강요를 만들지 않는다. 리뷰, 실시간 영업, 예약 가능 여부, 가격, 혼잡도, 실제 입장 가능성을 API에 있는 것처럼 표현하지 않는다. API 레코드 수만큼 SEO 페이지를 자동 생성하지 않고, 필터 조합별 대량 페이지도 만들지 않는다.

## 12. P0 구현 순서 제안

1. `PlaceSummary` 정규화 기준과 목록 검색 Adapter 설계
2. 현위치·지역·키워드 검색 결과 화면 설계
3. 지도와 목록의 동시 탐색 흐름 설계
4. `PetPolicy`, `VisitInfo`, `InfoStatus` 정규화 기준 설계
5. 장소 상세 방문 판단 카드 설계
6. 후보 2~3개 비교 설계
7. 정보 부족 경고와 전화 확인 권장 문구 설계

이 순서대로 진행하면 첫 버전은 “장소를 찾는다”, “조건을 이해한다”, “후보를 비교한다”, “헛걸음 위험을 줄인다”는 핵심 흐름을 먼저 완성할 수 있다.
